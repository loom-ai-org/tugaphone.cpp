# Parity with the Python tugaphone

This port gives the same bytes as the Python package tugaphone 1.4.16a1 for each function it ports. The parity test proves this. It runs every golden record in C++ and compares the result with the Python output, byte for byte.

## How parity is tested

The goldens are in `tests/goldens/<module>.jsonl.gz`, one file for each module. `tools/dump_goldens.py` writes them with the reference interpreter, and `tools/goldens/<module>.py` holds the corpora for each module. Each record holds the inputs of one call and the Python output. An exception is recorded as its Python class name.

The corpora for each module are these:

- Every string literal of the reference tests, read from the tag `1.4.16a1`.
- Every dialect and lect code, with case variants and aliases.
- A rule-coverage set built from the module tables.
- Each lexicon noun that ends in -agem or has a hyphen, after a number.
- Acronyms and letter-digit codes between each leading and each trailing punctuation mark.
- The words that `float()` reads as infinity or NaN, inside sentences.
- The five version constants.
- Unicode probes and a seeded fuzz set.

The test `tugaphone_parity` prints one line for each module, such as `registry: 797 in, 797 checked, 0 mismatches, 0 expected divergences, 0 stale entries`. The test fails if a record has a mismatch, or if the number of records checked is not the count in the header. The file `tests/parity/expected_divergences.tsv` lists the records that do not match until a fix in a dependency lands, with the fix that each record waits on. A listed record does not fail the test. The test fails if a listed record matches or is not in the goldens. Then the entry must go from the list.

ctest runs one test for each module, `parity_<module>`, so `ctest -j` runs the modules in parallel. Under ASan the engine goldens take more than an hour. The sanitizer job thus sets `TUGAPHONE_LATTICE_CORE_STRIDE`, and `--stride <n>` checks every n-th engine record. A listed divergence of a record that is not checked is not counted.

Parity is tested on x86-64 Linux with glibc, with gcc and clang, at the baseline x86-64 level, at x86-64-v3 and with `-march=native`. It is not tested on aarch64 or on other systems. The Markov scorer calls `log` and `exp` from the C library, as Python does. Its parity thus needs a libm that gives the same bits as the reference libm. On 32-bit x86 the scorer does not hold parity. A corpus of 299,460 scorer records, the goldens and seeded synthetic models, was run on i386. With x87 floating point, 56,698 records differ. With `-msse2 -mfpmath=sse`, 79 perplexity records differ, because the i386 `log` and `exp` differ in the last bit.

## Python semantics the port keeps

Text is decoded to code points. `len`, indices and slices count code points. Ill-formed UTF-8 decodes to one U+FFFD for each maximal subpart, as `bytes.decode("utf-8", "replace")` does.

The case mappings, `isspace`, `isalpha`, `isupper`, `isdigit`, `isdecimal` and the regular-expression classes `\w` and `\d` come from tables. `tools/gen_unicode_tables.py` generates the tables from the reference interpreter, which uses Unicode 15.0. The port does not use ICU for these properties.

Each regular expression is ported as code that tries the alternatives in the same order as the Python engine. `int()` and `float()` accept the same text as Python. This includes Unicode digits, underscores between digits, surrounding whitespace, and `inf` or `nan` in any case. `int()` refuses more than 4300 digits. A float is written as its `repr`.

A Python set is a `std::set`, so the C++ set iterates in code-point order. The Python order depends on the hash seed, so the goldens write sets sorted.

## The Markov scorer

`tugaphone.langdetect` scores words with markovonnx 1.0.2a1. The port holds the part of markovonnx that tugaphone uses, in `src/markov.hpp`. This part is `MarkovChain.load` of a JSON model, `Vocabulary.encode` and `decode`, `_get_probs` and `MarkovChain.perplexity`. The four bundled models in `data/langdetect/` are read from their gzip files, as `gzip.open` reads them. Sampling, training and the ONNX export are not ported, because tugaphone does not use them.

Each probability is the same float64 value as the Python value. The port does the same float operations in the same order:

- The count rows are float32. A row total is numpy's pairwise sum in float32.
- The Kneser-Ney discounts are float64. The discount mass is numpy's pairwise sum in float64 of `min(discount, count)`, rounded to float32 and divided by the float32 total.
- The interpolation term `discount_mass * (1.0 / V)` stays float32, as numpy's scalar promotion keeps it.
- A context that has no row gives the float32 value of `1.0 / V`.
- The perplexity adds the logarithms in sequence order and clamps each probability at 1e-30.

The library compiles with `-ffp-contract=off`, so the compiler does not fuse a multiply and an add.

The goldens hold, for each bundled model, three probabilities from every count row and the full rows of 12 contexts. They hold the perplexity of every gold word, contact word and test string, and of random contexts and sequences from a seeded generator. They also hold synthetic models: order 0, 1 and 3, Laplace smoothing, fractional and wide rows, -0.0 counts, duplicate count keys and malformed JSON.

Known limits: a count key or a context index beyond the 64-bit integer range raises an error at load, where Python accepts it. A vocabulary without `<UNK>` fails at load. Python fails when it scores.

## Language detection

`tugaphone.langdetect` is ported in full, in `include/tugaphone/langdetect.hpp`. When a model is missing or does not load, `MarkovLangDetector.from_dir` returns no detector. Python returns None. `get_detector()` loads the bundled models once.

The goldens hold the score and the detected language of many words. These are the gold words, the model vocabularies, the contact words and the test strings. A grid of margins from -0.5 to 3.0, with each default side, covers every twelfth word.

## Code-switching

`tugaphone.codeswitch` is ported in full, in `include/tugaphone/codeswitch.hpp`. `split_runs` uses the Markov detector when the models load, and the letter and stopword heuristics when they do not. The goldens cover both paths: the dumper replaces `langdetect.get_detector` with a function that returns None for the fallback path.

`transcribe_contact` calls orthography2ipa.cpp for the contact lect (es-ES, fr-FR or en-US) and maps the result to Portuguese phones with the same tables. English words with an internal apostrophe, ASCII or U+2019, stay one word: `transcribe_contact("don't", "en")` gives "dant", as Python does. The goldens hold 216 such records.

## Accent forcing

`tugaphone.accent` is ported in full, in `include/tugaphone/accent.hpp`: the respelling rules, `respell_word`, `respell`, `Transform`, `AccentOverlay` and `force_accent`.

The eight default respelling rules are written as code, not as regular expressions. A user rule or a `Transform` is a regular expression that the user supplies at run time. For these, the port has an engine in `src/pyre.cpp` that gives the same matches as Python's `re` module. Its parser is a port of `re._parser`: it accepts the same syntax and raises `re.error` for the same patterns. Its matcher follows the `_sre` rules for case folding, word boundaries and `$` before a final newline. It also follows them for a repeat that matches the empty string, and for an empty match after a match in `sub`. The engine does not support `\N{...}`. It raises NotImplementedError for it.

Python's parser recurses once for each nested group and once for each nested conditional. When a pattern nests deeper than the recursion limit allows, Python raises RecursionError. The port parses and compiles with heap stacks, so its C++ stack does not grow with the nesting. It counts the frames that Python's parser would use, its helper calls included, and raises RecursionError at the same point. For a call of `Transform.apply` or `RespellRule.matches` from the top level of a script, this point is 496 nested groups or 991 nested conditionals. A Python caller that already uses more frames reaches the limit at a smaller depth: there Python raises and the port does not. Python also raises earlier when its parser issues a warning, such as for a possible nested set, because the warnings module adds frames. The port issues no warnings.

The matcher keeps its continuations, backtrack points and group mark changes on heap stacks, so its C++ stack does not grow with the subject. It calls itself once for each nested lookaround, atomic group and possessive repeat, and the parser limits that nesting to 495 levels. Each level uses about 0.5 KB of stack in a Release build and about 1 KB in a Debug or sanitizer build. The engine thus needs a stack of 1 MB on the thread that calls it. The main thread of a Linux process usually has 8 MB. The goldens hold subjects of 100,000 code points and patterns nested from 400 to 20,000 levels deep. ctest runs the accent records on a thread with a 1 MB stack.

The table gives the smallest stack on which all the `nesting` records pass, measured in steps of 4 KB with `tugaphone_parity --stack-kb`. The record that needs the most stack is 495 nested possessive repeats, `(?:` ... `a` ... `)*+`. This stack includes about 75 KB that the parity harness uses itself.

| Build | Stack |
| --- | ---: |
| GCC 16, Release (`-O3`) | 320 KB |
| clang 23, Release (`-O3`) | 340 KB |
| GCC 16, Debug (`-O0`) | 568 KB |
| clang 23, Debug with ASan and UBSan (`-O1`, the CI `sanitizers` job) | 552 KB |

`respell_word`, `respell` and `force_accent` take the phonemizer as an argument. Without one, they use the lattice phonemizer, `lattice_core::phonemize`. The accent goldens use a deterministic stand-in phonemizer, which `tools/goldens/accent.py` and `tests/parity/accent.cpp` both define. The stand-in tests the hill-climb, the case restoration, the word spans and the overlay stages. The lattice-engine goldens call `respell_word` and `force_accent` with the default phonemizer.

The goldens hold the default rule matches over every gold word. They hold the respelling of every gold word for its own lect and for pt-PT-x-porto, and of the mixed sentences, with each dialect in turn. They also hold 244 regular expressions, valid and invalid, over Unicode subjects, with and without IGNORECASE. The corpus `nesting` holds groups, lookarounds, repeats, possessive repeats and conditionals nested at depths on both sides of Python's recursion limit. Its conditionals nest in the "yes" branch and in the "no" branch. The corpus `matcher_guards` holds repeats whose body can match the empty string and backreferences to empty groups. In these patterns, a conditional changes its branch once its group is set, so each guard of the matcher on empty iterations changes the result.

### Speed and memory of the regular expression engine

`tools/bench_regex.py` measures the engine against Python's `re`. Each case is one `re.sub(pattern, "X", subject, flags=re.I)` over a long subject. The script runs the case in a new Python process and through `tugaphone_parity` in a new C++ process, three times each. It shows the shortest wall time and the peak RSS of each process, and it checks that the C++ result is equal to Python's. The `baseline` row uses a pattern that never matches: it shows the cost of process start, data loading and golden parsing.

```
python -I tools/bench_regex.py build
```

The table comes from a Release build with gcc on x86-64. The machine ran other jobs, with a load of about 20 on 8 CPUs, so the times vary by about 30 % from run to run.

| Case | Subject (code points) | Python s | C++ s | Python MB | C++ MB |
| --- | ---: | ---: | ---: | ---: | ---: |
| `baseline` | 1,000,000 | 0.05 | 0.11 | 15 | 22 |
| `a*` | 1,000,000 | 0.05 | 0.20 | 15 | 144 |
| `\w+` | 1,000,000 | 0.04 | 0.28 | 15 | 146 |
| `(a\|b)*` | 1,000,000 | 0.19 | 0.74 | 92 | 422 |
| `(?:(a)\|b)*` | 1,000,000 | 0.21 | 0.69 | 158 | 369 |
| `(?:(?=(a\|b))\1)*` | 1,000,000 | 0.17 | 0.74 | 92 | 374 |
| `(?:a\|b)*+` | 1,000,000 | 0.05 | 0.18 | 15 | 15 |
| `(?=(a\|b)*$)`, quadratic | 5,000 | 1.00 | 8.09 | 15 | 15 |
| `(a+)+c`, exponential | 18 | 0.06 | 0.15 | 15 | 15 |

Time and memory grow linearly with the subject in both engines, but the C++ engine is 2 to 8 times slower and uses up to 10 times more memory. The matcher keeps a backtrack point and a continuation frame on the heap for each iteration of a repeat. sre matches a repeat of one character in a single loop that keeps no state per iteration. A pattern that scans the rest of the subject from each position is quadratic in both engines. A pattern with nested repeats that cannot match is exponential in both engines. The user patterns of an accent overlay apply to one word or one sentence at a time, so these costs are small in normal use.

## The lattice engine

`tugaphone.lattice_core` is ported in full, in `include/tugaphone/lattice_core.hpp`. The engine of a lect is an `orthography2ipa::G2P` from orthography2ipa.cpp. The C++ G2P has no `normalizer=` argument. Thus `engine()` registers the tugaphone normalizer as a normalize plugin named `tugaphone:<lect>` and names it in the plugin overrides of the engine. The Python G2P runs the normalize plugins of the spec and then the normalizer of the caller. No Portuguese spec declares a normalize plugin, so the order is the same. The normalizer applies `normalize_orthography`, then `normalize_numbers`, then the bifonia homograph marks.

The engine registers the tugalex lexicon of the lect before it builds the G2P. It writes the lexicon TSV to `lexicon_cache_dir()`, with a stamp file that holds the tugalex release, `tugalex::kPythonReference`. `TUGAPHONE_LEXICON_DIR` sets the directory, and `set_lexicon_cache_dir()` replaces it, as a test replaces the Python module attribute. The directory and the stamp path are the strings that `pathlib` gives, and a failure to write the cache raises the `OSError` subclass that Python raises for the same `errno`. A contact mode other than "none" splits the text with `codeswitch::split_runs` and transcribes each contact token with `codeswitch::transcribe_contact`. `phonemize_runs()` is the loop that joins the runs. The goldens also call it with a fixed contact transcriber, which `tools/goldens/lattice_core.py` and `tests/parity/lattice_core.cpp` both define.

The goldens of the engine are these:

| Corpus | Records |
| --- | --- |
| Each of the 41 lects over the 4,541 unique gold-TSV words | 186,181 |
| Each gold-TSV row through the lect of its file | 10,093 |
| The test strings through 7 lects | 10,360 |

Every engine record matches at the submodule pin, so `tests/parity/expected_divergences.tsv` lists no record. `engine(lect).features()` and `engine(lect).sentence_lattice()` apply the tugaphone normalizer through the plugin override, as `transcribe()` does, and the goldens call both methods with numbers, abbreviations and homographs.

Two cache cases do not match Python:

- A stamp file that is not UTF-8. Python raises `UnicodeDecodeError` from each `phonemize` call until the file is deleted. The port reads the stamp as stale and writes the cache again. A port of the crash would make a broken cache permanent, and no caller can depend on it.
- A cache TSV that was not written by the engine, with a current stamp. orthography2ipa.cpp `load_lexicon` folds the case of each key, keeps a trailing carriage return and reads everything after the first tab. Python keeps the key as it is and skips a line that does not have two fields. The engine writes neither case, so only a TSV changed by hand reaches it. The difference is in orthography2ipa.cpp.

orthography2ipa.cpp keeps its specs, lexicons, plugins and regular-expression caches in global maps with no lock. The engine cache, the lexicon registration and each transcription hold `detail::o2i_registry_mutex()`. The contact engines of codeswitch hold it too. The test `threads_lattice_core` makes eight first `phonemize` calls in eight threads. The test `threads_tokenizer_codeswitch` builds tokenizer sentences in four threads and makes contact transcriptions in four others. CI runs the `threads_` tests under ThreadSanitizer. The test `threads_package` makes the first calls of ten package entry points in ten threads: the `TugaPhonemizer` methods, the plugin classes and the command line. With the lock made thread-local, ThreadSanitizer reports 35 races in it.

## The package API, the plugin and the command line

`include/tugaphone/tugaphone.hpp` holds `TugaPhonemizer` and the names that the Python package exports at its top level. `phonemize_sentence` and `force_accent` call the lattice engine. The deprecated `regional_dialect` argument has no effect, as in Python. `include/tugaphone/plugin.hpp` holds `TugaphoneG2PPlugin` and `SilabificadorSyllabifier`. The executable `tugaphone` is the console script `python -m tugaphone`.

The goldens of these parts are these:

| --- | --- |
| `phonemize_sentence` of each of the 41 lects over the 4,541 unique gold-TSV words, five contact modes in each record | 186,181 |

| The error lines of overlay JSON, UTF-8 decoding and regular expressions, in the process | 7,036 |

The command-line records run `python -I -m tugaphone` and the C++ executable on the same arguments, and compare standard output, standard error and the exit status. When Python ends with a traceback, for example for an overlay file that does not exist, the record holds the last line of the traceback: the exception class and its message. The C++ executable prints that line alone and exits with status 1. The path of this repository reads as `<root>` in that line. This holds for the exceptions of the libraries too: an unclosed `<phoneme>` tag gives `orthography2ipa.markup.MarkupError`, and a lexicon cache that cannot be made gives the `OSError` subclass of its errno, with the path that failed.

Some command-line records change how the process runs. Six records set the lexicon cache under a file, under `/proc`, under `/dev/null`, or under a home or cache directory that does not exist. Four records write standard output to `/dev/full`: Python then exits with status 120 and prints the `OSError` of the flush, and so does the C++ executable. Both executables write standard output as Python's `sys.stdout` does. Up to 8,192 bytes wait in the text layer, over a buffer of the block size of the descriptor. A longer output reaches the descriptor inside `print()`, so a failed write there is an uncaught `OSError` with its own errno, and the status is 1. `tests/cli_process.sh` checks this for `/dev/full` and for a closed pipe. It also checks that a short output into a closed pipe exits with 120, because both executables ignore SIGPIPE. Four records run standard output on a pseudo-terminal of a given width with `COLUMNS` unset, so the help wraps at the width of the terminal. Arguments that are not UTF-8 decode as Python's `surrogateescape` does, and an error message shows such a byte as `\udcff`. A `COLUMNS` value above the range of `long` means a width that never wraps, as a Python int does.

Other records run in the process and compare the line that an uncaught exception prints. They hold 2,016 malformed and valid overlay JSON texts, 4,863 byte strings decoded as UTF-8, and 157 malformed regular expressions and replacement templates. So the `json.decoder.JSONDecodeError` message with its line, column and code-point position, the `UnicodeDecodeError` byte range and reason, and the `re.error` position match Python. The test `cli_process` checks two cases that no golden can hold: without the tugalex or bifonia data, the executable prints one error line and exits with status 1, and the benchmark exits with status 120 when standard output is `/dev/full`.

The acceptance sentence is "Tenho 23 anos, Sr. Silva; li o Cap. XII.". The Python command line has no `--contact` flag, so the contact modes of this sentence are in the `phonemize_sentence` records. The command-line records hold the sentence in every lect, and the `--contact` arguments as the error that argparse gives.

Every package and plugin record matches with the orthography2ipa.cpp submodule pin, with no listed divergence.

## The benchmark

`tugaphone_benchmark` is the port of `scripts/benchmark.py`. It reads the gold fixtures in `tests/data/gold/`, scores the rules-only transcription of each word, and writes `benchmarks/results.json` and `docs/scoreboard.md` under the directory it runs in. `TUGAPHONE_BENCHMARK_ROOT` names another directory. `--refresh-fixtures` downloads the gold in Python. The C++ tool does not download, so it prints a message and exits with status 2.

The goldens hold every fixture word with its transcription, edit distance, stress result and confusion pairs. They hold probes of the scoring helpers, including strings of 200 code points and more for the difflib "popular element" rule, `score_dialect` with 8 limits, and 35 runs of `main`. A run with no arguments gives the same summary lines and the same two report files, byte for byte. When `main` raises, the record holds the last line of the traceback, with the scratch root as `<root>`. Two runs have a regular file where `main` makes the `benchmarks` directory: the run that writes the reports prints its summary lines, then `FileExistsError`. `--dialect` joins the fixture path as `os.path.join` does, so `--dialect /dev/null` reads `/dev/null.tsv`.

The reports that the Python repository commits at the tag do not match what its script gives with the reference packages. For example, pt-BR has a PER of 0.2448 in the committed file and 0.2365 from the script. The C++ tool reproduces the script.

## Python defects kept for parity

The port keeps these defects of the reference release, because it is held at byte parity:

- ovos-number-parser drops the feminine after a scale group: feminine 1001 reads "mil e um".
- ovos-number-parser keeps the masculine count before a feminine ordinal scale word: feminine ordinal 2002 reads "dois milésima segunda".
- ovos-number-parser compares the language code with its case, so "PT-PT" raises NotImplementedError.
- `EuropeanPortuguese` and `BrazilianPortuguese` replace an empty `IRREGULAR_WORDS` with the lexicon map. The African and Timorese classes keep an empty map.
- `normalize_numbers` takes each word that Python `float()` accepts as a number, then calls `int()` on it. In strict mode, "o Inf. Henrique", "nan" and "Infinity" raise ValueError. Without strict mode, the word stays as it is.
- `expand_letter_digit_codes` calls `int()` on the digits of a code, so a code with more than 4300 digits raises ValueError. `normalize_orthography` raises too.
- markovonnx takes `context[-order:]`, which is the whole context for an order-0 model. An order-0 model gives the uniform probability for every context that is not empty.
- `Transform.from_dict` reads `ignore_case` with `bool()`, so the string "false" turns case folding on.
- A `word` transform puts `\b` on each side of the pattern. A pattern that starts or ends with punctuation thus never matches between spaces.
- `AccentOverlay.from_dict` writes any name with `str()`: a null name becomes "None".
- The tokenizer gives a grapheme and a character an `idx_in_sentence` of `-1 + idx_in_word`. The value does not add the offset of the word in the sentence.
- `is_grapheme_silent` compares the prefix with `"m"` and tests `after[0] in "cç"` for the archaic silent p. A direct call with the prefix `"m"` returns true. `CharToken.is_silent` gives the whole word prefix, so the rule never fires for a character of a word: `assumpção` keeps its p. The `mpt` words never match, because t is not in `"cç"`.
- `scripts/benchmark.py --limit 0` formats a missing PER with `:.4f` and raises TypeError.
- A negative `--limit` drops the last words of each fixture, as a Python slice does.

### tugaphone.tokenizer

A Sentence owns its WordTokens, a WordToken owns its GraphemeTokens, and a GraphemeToken owns its CharTokens. Each token keeps a pointer to its parent, so a token cannot be copied or moved. A Python `cached_property` is computed on first use and then kept. The dialect of a token is a `std::shared_ptr<const DialectInventory>`, and a null pointer stands for a new `EuropeanPortuguese()`.

The constructors take the Python arguments, except `graphemes=` of WordToken and `characters=` of GraphemeToken. In C++ a parent always builds its children, because each child must point at its parent. `features` returns the dict as an ordered list of key and value pairs, and `features_json()` writes it as `json.dumps` does. `unicodedata.normalize("NFD")` and `unicodedata.combining` come from `src/unicode_norm.hpp`, the tables that the language detector also uses.

The goldens use 13 dialects: the five national classes, the three city classes, the base `DialectInventory`, and four dialect codes given to a national class. Two of the codes are regional, and no class knows the other two. A record holds the IPA and the features of the sentence. In the five national classes it also holds every property of every word, grapheme and character token. A sentence of up to 12 characters has the full text of these properties, and a longer one has a CRC-32 and a length.

| Corpus | Records |
| --- | --- |
| Module functions and constants | 1,806 |
| Test strings, token properties, national classes | 7,400 |
| Test strings, IPA, the other eight dialects | 11,840 |
| The 4,541 unique words of the 10,093 gold-TSV rows, IPA, 13 dialects | 59,033 |
| Every 20th gold-TSV word, token properties, national classes | 1,140 |
| Unicode probes | 228 |
| Seeded fuzz | 1,500 |
| Tokens built directly, parent links, diaeresis vowels and rare graphemes | 308 |
| Total | 83,255 |

The rare graphemes are the tetragraphs of "Uruguai" and "quais", the triphthong of "saguão", the final o after a silent h in "Soho", and the atonic "pra". Only caller syllables, such as `["assu", "mpção"]`, put an archaic `mpç` or `mpt` grapheme in a word, so the goldens build these words with their syllables.

orthography2ipa.cpp keeps its spec cache in a global map with no lock. The tokenizer holds `detail::o2i_registry_mutex()` while it loads a spec, so threads can build sentences of different dialect codes at the same time. The test `threads_tokenizer` builds eight sentences in eight threads, and CI runs it under ThreadSanitizer.

### tugaphone.plugin

The OVOS plugin registration is not applicable. A Python package registers a plugin with an entry point, and C++ has no entry points. A C++ program that wants `SilabificadorSyllabifier` as the syllabifier of orthography2ipa.cpp calls `orthography2ipa::register_syllabifier_plugin`. orthography2ipa.cpp keeps its plugins in a global map with no lock, and the lock that tugaphone holds around a transcription is not in the installed headers. So the program registers the plugin before its first transcription, while it has one thread. tugaphone 1.4.16a1 itself declares no entry point: the `orthography2ipa.syllabify` group gets its Portuguese syllabifier from orthography2ipa.
